# 平台内容库 + 双端（管理端 / 用户端）· 设计草案

> **状态：草案，待讨论，未定稿。**
> 不进 `PRD` / `ARCHITECTURE` / `ROADMAP`，也不动代码——讨论收敛后再往权威文档里落。
> 出发点：用户做模拟面试时，**公司档案与面经不该由用户自己搜、自己整理**，而应由平台维护。

---

## 0. 一句话定性

这不是「加个后台页面」，而是让系统**第一次拥有不归任何租户、所有用户共享**的业务数据。它直接顶到既有架构不变量——**「每个业务表都带 `user_id`，由拦截器强制注入」**。要做，就得给这批数据一个**显式的「平台」身份**，并证明**合并平台库不会让 A 看到 B 的数据**。

文档其实预留过方向（BRD §3 `平台运营/客服` 列为 P1；PRD §1「运营后台本期仅设计占位、不实现」且「不得直接读取用户业务内容」；ARCHITECTURE §2 已列「管理端与用户端权限域隔离」的双 token 拦截器为未来参考）——但都被**明确推后**。把它提上来是**产品范围决策**。

## 1. 已确认的四个方向（用户拍板）

1. **内容归属**：平台库 **+** 用户可私有（两份叠在一起检索）。
2. **管理端形态**：**独立后台 + 独立认证**（双 secret / 双 token）。
3. **运营可见性**：**看不到用户业务内容**（红线；只看聚合/脱敏）。
4. **本轮**：**先出设计**，不动代码。

## 2. 数据所有权：三种

| 归属 | 例子 | 隔离规则 |
|---|---|---|
| **租户私有** | 简历、用户导入的文档、记忆、投递、对话 | `user_id = 租户`，拦截器强制（现状不变） |
| **平台公开**（新） | 公司档案（含难度档位）、平台面经 | `owner = PLATFORM`，**所有用户可读**，无 `user_id` |
| **运营数据**（新） | 导入任务、审核记录、用量聚合 | 仅管理端，**脱敏** |

## 3. 核心难点：平台数据放哪（三选一）

### 选项 A（**推荐**）· 同表 + `owner` 列 + 受控的跨租户读
- `kb_document` / `kb_chunk` 加 `owner VARCHAR(16)`（`USER` | `PLATFORM`）；平台行 `user_id` 置 **NULL**。
- 平台行的读写走**显式 `@InterceptorIgnore` 的 mapper 方法**，SQL 里硬写 `owner='PLATFORM'` —— 跨租户面被限制在「只读平台行」这一件事上，**可审计**（先例：`KbDocumentMapper` 的那四个队列方法，注释里已论证过「仅有的跨租户面」）。
- **检索合并**：向量侧 `where` 用 `$or: [{user_id:<tenant>}, {owner:'PLATFORM'}]`；回捞原文「本租户 ∪ 平台」。
- 好处：一张表、**一套切分/嵌入/检索链路**，平台面经和图库简历共用。代价：**动了拦截器的假设**，必须把「平台行」的论证写死在注释里。

### 选项 B · 独立平台表（`platform_document` / `platform_chunk`）
- 平台数据完全不进租户表，**拦截器不用动**。
- 代价：切分/嵌入/检索/导入全要**第二套**（或抽「双来源」抽象），重复面大。

### 选项 C · 平台当「特殊租户」（`user_id='platform'`）—— **不推荐**
- 最省事，但「平台租户」会被当成真租户：用量、配额、注销、上限全要特判；检索要查两个租户。**把架构的例外藏在数据里，最难维护。**

## 4. 双端认证（ARCHITECTURE 早有预设）

- **两条独立认证域**：用户端 JWT（现状）+ 管理端 JWT——**不同 secret、不同 issuer、不同路径前缀**（`/api/v1/admin/**`，独立拦截器）。
- 管理端主体 = **`platform_admin`（不是租户）**，**不产生 `UserContext`**。**管理端请求绝不能带租户上下文**——否则一处疏忽就跨租户了。
- **「看不到用户内容」用「没有这个接口」来实现，而不是用权限去拦**：管理端**根本没有**读简历/记忆/对话的 Controller。这是最硬的实现方式——比 RBAC 白名单可靠得多（少一条「配错了就能看」的路）。管理端只暴露**聚合/脱敏**接口（用量汇总、失败率、异常计数）。

## 5. 检索合并的正确性（最要紧，必须用测试钉死）

**要证明的命题**：合并平台库，**不会**让 A 看到 B 的数据。

- 用户侧向量 `where` = `user_id=<A> OR owner=PLATFORM`。
- 平台行只有 `owner=PLATFORM`、**无 `user_id`**；B 的行是 `user_id=B 且 owner=USER`——既 ≠ A 也 ≠ PLATFORM，**结构上不可能被命中**。
- **回归测试**：播种 A、B 各一篇 + 平台一篇 → A 的检索**只返回 A + 平台**，绝不返回 B。（与现有 `TenantIsolationIntegrationTest` 同款断言。）

## 6. 导入链路复用

- 平台导入**走同一套** `DocumentIngestService`（切分 / 嵌入 / Chroma upsert），只是 `owner=PLATFORM`、`user_id=NULL`、由管理端触发。
- **要处理 worker 的 `UserContext` 假设**：现有 worker 认领后把行的 `user_id` 写回 `UserContext`；平台任务没有租户 → 需要一条「平台任务」的认领/处理分支（或让 `owner` 决定走不走租户上下文）。

## 7. 合规（面经/公司数据的来源）—— 风险不在技术，在内容

- 面经来自网络 → **版权 + 个人信息**（PRD NFR-6 很在意）。
- 建议：管理端导入**强制填「来源 / 授权备注」**，且支持**一键下架**（下架同时清向量，复用现有删除/重建链路）。
- 这是**产品/法务**问题，不是工程能独自拍板的——先记下来。

## 8. 分端功能清单（草稿，供改）

| 功能 | 用户端 | 管理端 | 数据归属 |
|---|---|---|---|
| 简历/材料、问答、投递、记忆 | ✓ 私有 | **无接口**（看不到内容） | 租户私有 |
| 模拟面试（发起 / 作答 / 报告） | ✓ | 维护公司库 / 面经库 / 难度档位 | 公司/平台面经 = 平台 |
| 面经导入 | ✓ 可私有 | ✓ 平台批量导入 | 平台 + 用户私有 |
| 用量 / 配额 | 看自己 | 看聚合（脱敏） | — |
| 记忆候选审批 | 用户自己批 | 不介入 | 租户私有 |
| 用户管理（禁用 / 重置凭证） | — | ✓（**不含内容**） | — |
| 内容审核 / 下架 | 举报入口 | ✓ | 平台 |
| 运营看板 | — | ✓ 聚合 | — |

## 9. 与现有迭代的关系

- 这是一个**比 I-4 更大的产品转向**，应立成**新迭代**（如「内容平台」），而不是塞进 I-4。
- 它其实**解锁了 US-3 面试模拟官的真正玩法**：现在 `doc_type=INTERVIEW` 是「用户自导入」，改成平台库后，面试官才第一次**有真面经可依**。所以两者应**一起设计**。
- 触及面：`ai`（检索合并）、`knowledge`（owner 列 / 导入分支）、`security`（第二条认证轴）、新 `admin` 包、前端 `frontend/admin/`。

## 10. 开放问题（要一起定，再动手）

1. **平台库版本**：公司难度档位改了，历史面试会话怎么算（创建时快照？回放？——现在 `interview_session` 已经快照了 `resolved_difficulty`，这是个好底子）。
2. **用量口径**：用户检索**命中了平台内容**，算不算该租户的检索消耗？（PRD-FP-10 的计量要不要区分「读自己的」与「读平台的」）
3. **多管理员与审计**：谁导入了什么、谁下架了什么——要不要一张操作留痕表。
4. **去重**：平台面经与用户私有面经可能重复，检索时要合并还是去重。
5. **平台内容的可见范围**：所有用户全见，还是按公司/岗位/难度分域？
