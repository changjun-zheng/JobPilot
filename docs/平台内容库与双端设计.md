## 0. 一句话定性

让系统**第一次拥有不归任何租户、所有用户共享**的业务数据。它顶到既有不变量——**「每个业务表都带 `user_id`，由拦截器强制注入」**。要做，就得给这批数据一个**显式的「平台」身份**，并证明**合并平台库不会让 A 看到 B 的数据**。

## 1. 已确认的方向

## 2. 平台内容其实是**两种形态**（v2 新增——原草案漏了）

原草案只想了「面经=文档」。但你说的「公司 / 岗位 / 难度」是**结构化数据**，不是可检索文本。所以平台内容分两类：

| 形态 | 例子 | 存法 |
|---|---|---|
| **结构化目录** | 公司（名称、难度档位、行业、标签）、岗位（后端/算法/前端…）、**公司×岗位**（哪家公司招这个岗位） | **新表**（见 §3），平台级、无 `user_id` |
| **非结构化文档** | 面经、公司介绍长文、考点清单 | `kb_document` 加 `owner=PLATFORM` + **关联 `company_id`**，走检索 |

两者**互相引用**：面经文档挂到某个 `company_id`（可再挂岗位），于是「这家公司的面经」= 按 `company_id` 过滤的检索。

## 3. 数据模型（v2 补全）

**结构化（新表，平台级、无 `user_id`）**
- `platform_company`：`id` / `name` / `tier`（难度档位，对应现有 `jobpilot.interview.tiers`）/ `industry` / `tags` / `status`（上架/下架）。
- `platform_position`：`id` / `name`（如「后端开发」）。
- `platform_company_position`：`company_id` × `position_id` —— 支撑「**有这个岗位的公司**」这个查询。

**非结构化（改现有表）**
- `kb_document` / `kb_chunk` 加 `owner`（`USER`/`PLATFORM`）；平台行 `user_id=NULL`；面经再加 `company_id`（可空，公司介绍/通用考点为空）。
- 平台行的读写走**显式 `@InterceptorIgnore` + SQL 里硬写 `owner='PLATFORM'`** 的 mapper 方法（先例：`KbDocumentMapper` 的队列方法，注释里论证「仅有的跨租户面」）。
- **检索合并**：向量 `where = user_id=<租户> OR owner=PLATFORM`，再按 `company_id`（用户选的公司）收窄。

**面试会话（改现有表）**
- `interview_session.company`（自由文本）→ 改成引用 `company_id`（平台目录）；同时**保留文本快照**（公司在库里改名/下架后，历史面试仍可读）。

## 4. 面试设置流程（v2，来自你的描述）

```
选目标：公司  ┃  岗位
   ├─ 选公司 → 取该公司的难度档位/面经
   └─ 选岗位 → 列出「招这个岗位的公司」（platform_company_position）
                → 勾选 1..N 家
        ↓
开始模拟面试（检索 = 选中的公司面经 + 我的简历；难度 = 公司档位）
```

> **「勾选 1..N 家」= 混成一套题**（v3 定）：把这几家的面经并进同一次检索、难度取综合（如最高档），
> 出一套**综合题 + 一份报告**——不逐家分轮、不打对比报告。这样面试仍是一段连贯对话，符合现有会话模型。

## 5. 检索合并的正确性（不变，必须用测试钉死）

**命题**：合并平台库**不会**让 A 看到 B 的数据。
- 用户侧 `where = user_id=A OR owner=PLATFORM`。
- B 的行是 `user_id=B 且 owner=USER` —— 结构上不可能命中。
- **回归测试**：播种 A、B 各一篇 + 平台一篇 → A 的检索只返回 A + 平台。

## 6. BYOK（用户自带模型）——与现有设计**直接冲突**（v2 新增，重点）

现在：`JOBPILOT_AGENT_PROVIDER_PATH` 是**全局配置**，一处开关决定全平台走哪个 provider（§「一处开关」）。
BYOK 要求：**模型来源按租户**——A 用平台模型、B 用 B 自己的 key。

**这不是加个字段，是模型装配从「全局单例」变成「按租户解析」**：
- `ChatPort` / `EmbeddingPort` 的**选择**要下沉到「每次调用看当前租户的配置」；现在是 Bean 装配期一次性决定。
- 涉及**存用户密钥**（必须加密存、绝不明文/日志）；且 `AiProviderConsistencyCheck` 那套「全局一致」的断言对 BYOK 不适用。
- **用量口径跟着变**：平台模型的调用 = 平台成本（要计量、要配额）；BYOK 的调用 = 用户自己的账（平台不该拦、也不必计费——但仍要计量以便诊断）。
- **合规**：用户把 key 交给你保管，是新的信任面。

**建议**：现在**只在设计上留接缝**（把「模型来源」抽成一个「按租户解析」的接口，当前实现恒返回平台配置），**不实现**。这样 BYOK 落地时不用重写装配。

## 7. 分端功能清单（v2 修订）

| 功能 | 用户端 | 管理端 | 归属 |
|---|---|---|---|
| 简历/材料、问答、投递、记忆 | ✓ 私有 | **无接口** | 租户私有 |
| 模拟面试 | ✓ 发起/作答/报告 | 维护公司·岗位·难度·面经 | 目录/面经 = 平台 |
| 公司/岗位浏览筛选 | ✓ | ✓ 增删改 + 上下架 | 平台 |
| 面经导入 | ✓ 可私有 | ✓ 平台批量导入（关联到 company/position） | 平台 + 私有 |
| 模型来源 | 现在用平台的 | 配平台模型 | **BYOK 后按租户** |
| 用量/配额 | 看自己 | 看聚合（脱敏） | — |
| 内容审核/下架 | 举报入口 | ✓（下架同时清向量） | 平台 |

## 8. 合规（面经/公司数据来源）

版权 + 个人信息（PRD NFR-6）。管理端导入**强制填来源/授权备注**，支持**一键下架**（复用删除/重建链路）。产品/法务问题，工程不独自拍板。

## 9. 与现有迭代的关系

比 I-4 大的产品转向，应立**新迭代**。它**解锁 US-3 的真正玩法**（平台面经 + 公司难度），也是现在 `doc_type=INTERVIEW`（用户自导入）的升级方向。
