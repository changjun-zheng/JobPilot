## 1. 产品概述

### 1.1 产品目标

JobPilot 将以下流程集中到一个带个人知识库的 Agent 工作台：

```text
注册账号
    → JD / 个人材料导入
    → 知识库检索与引用问答
    → JD 分析与匹配
    → 面试准备与模拟追问
    → 投递记录
    → 复盘与弱点沉淀
```

产品同时服务两个目标：

1. **产品价值**：让求职者用一个人账本替代散落的 Excel、聊天记录和临时笔记，并且其私密材料始终归属于自己、可导出可删除。
2. **工程目标**：以多租户隔离、RAG 检索质量、Agent 控制流与可观测性为骨架，构建可对外稳定提供服务的后端系统。

### 1.2 目标用户

| 用户 | 本期定位 | 需求 |
|---|---|---|
| 校招求职者 | 主要用户 | 批量处理 JD、按优先级准备面试、管理投递进度 |
| 社招 / 转行求职者 | 主要用户 | 用历史经历匹配新岗位、整理跨行业信息 |
| 海投型高强度求职者 | 主要用户（能力支持） | 高频投递记录、批量 JD 分析、阶段复盘 |
| 平台运营 / 客服 | 内部角色，无业务数据写权限 | 用户支持、异常排查、合规处置 |
| 机构管理员（高校 / 培训机构） | P2，本期不做 | 批量开户、组织级配额与统计 |

所有外部用户**各自独立注册、数据互不可见**。产品不区分「管理员能看用户数据」的形态——运营侧排查需走脱敏与授权流程，见 §8。

### 1.3 产品原则

- **领域优先**：所有 Agent 能力围绕求职，不做通用 chatbot。
- **租户隔离优先**：任何业务数据读写都必须带租户归属；隔离由数据访问层强制保证，不依赖调用方自觉。**功能可以延期，隔离不能妥协。**
- **证据优先**：涉及个人经历和知识库的问题尽量给出原文引用；无依据时明确说明未知。
- **人工掌控副作用**：会写入知识库或长期记忆的 AI 产物必须经过用户确认。
- **用户数据主权**：用户可随时导出、删除自己的全部数据；删除必须覆盖数据库、向量库与原始文件三处。
- **先同步后流式**：先完成可测试的同步闭环，再叠加 SSE。
- **评测驱动**：检索质量以固定评测集衡量，不以主观演示替代。
- **按容量设计，不按想象设计**：容量上限显式写在 NFR 里，触达前先垂直扩容，不为不存在的大流量提前做分布式架构。

### 2.2 明确不在本期

以下内容保留在 P2 backlog，不得以「顺手实现」的方式进入本期验收：

- 组织 / 部门 / 成员邀请等多层级权限模型（含机构批量开户）；
  > **不是 RBAC 的延后，而是 RBAC 的前提尚未出现。** 本期租户 = 一个自然人用户，租户内只有一个用户，**没有权限可分配**，因此根本不使用 RBAC。多租户（数据隔离）与 RBAC（授权）是两个正交的轴，概念澄清见 `docs/ARCHITECTURE.md` §1.7.1。
- 订阅计费与支付渠道对接；
- 多模型路由、自动模型选择；
- 招聘平台爬虫、平台对接和自动投递；
- 面向招聘方 / HR 的候选人管理能力；
- 社区与社交功能（面经分享、互评）；
- PDF 表格结构还原、扫描件 OCR、PDF 渲染和复杂简历排版；
- 投递看板、移动端、实时协同和多端同步；
- 求职周报、上下文摘要治理、复杂记忆治理；
- 分库分表、多机房容灾、分布式向量库和亿级数据容量设计。

> **原 v0.4 §2.2 中的「JWT 注册、登录和完整权限系统」已移出本节，升为 P0（FP-9）。** 多租户产品没有鉴权便无法对外提供服务，它不再是可延后的加固项。

## 3. 角色、前置条件与身份边界

### 3.1 角色

本期只有两个角色：

**求职者用户（外部）**——可以：

- 注册、登录、登出、维护自己的账号凭证；
- 导入、查看、删除自己的文档；
- 查询和使用自己的知识库；
- 发起对话、JD 分析和模拟面试；
- 查看、创建和更新自己的投递记录；
- 审批 AI 生成的持久化草稿；
- 查看自己的记忆、用途说明、用量配额与 Agent trace 摘要；
- 导出个人数据、注销账号。

**平台运营（内部，本期仅为设计占位）**——不得直接读取用户业务内容。异常排查必须走脱敏样本或用户显式授权，且操作留痕。本期不实现运营后台。

### 3.2 身份处理

- **注册登录纳入本期 P0**。首版支持邮箱 + 密码注册登录；手机号、第三方登录为 P2。
- 鉴权采用无状态凭证（JWT 或等价方案），由 JobPilot 自行签发与校验，不依赖外部身份服务。
- 所有持久化业务对象必须带租户归属键 `user_id`；**任何查询、修改和删除操作都必须按 `user_id` 隔离，无例外**。
- 租户条件由数据访问层统一注入，业务服务不得手工拼接 `user_id` 条件，也不得从请求参数信任客户端传入的 `user_id`——服务端一律以凭证中的身份为准。
- 跨租户访问统一返回 404（不泄漏资源是否存在）或 403（明确越权），并写入安全日志。
- 用户名、邮箱、密码哈希等凭证信息不得出现在日志、trace 与错误响应中。

### 3.3 前置条件

完整 AI 闭环需要以下外部服务：

| 依赖 | 用途 | 当前状态 |
|---|---|---|
| AI 接入层 | 统一 Chat/Embedding/Tool Calling 供应商协议 | I-0 已落地 Spring AI 2.0.1；业务层只依赖 JobPilot 自定义 Port，不引入 LangChain4j |
| MySQL | 账号、元数据、文本、会话、记忆、投递、用量、trace | I-0 已接入（Flyway 建表）；是**启动前置**，无库则应用起不来 |
| 向量库（默认 Chroma） | Chunk 向量存储与相似度检索 | I-0 已接入；Port 抽象须允许替换为托管向量库 |
| 本地 Ollama + `bge-m3` | 默认嵌入路径（零边际成本） | I-0 已接入 |
| 云端 Embedding / LLM API | 可选路径，按租户计量 | I-2 补齐配置化与切换 |
| Redis | 凭证黑名单、限流、会话缓存与幂等键 | P1 起按需引入，不作为 P0 闭环前置 |

> **部署形态说明**：本地 Ollama 是**默认路径而非唯一路径**。当部署方不具备本地 GPU 或面向云端用户时，必须能仅通过配置切换到云端 embedding，而不改业务代码。

## 4. 核心用户流程

### 4.1 注册与登录

```text
用户访问 → 输入邮箱与密码注册
    → 校验邮箱格式与密码强度、检查是否已注册
    → 创建账号（密码加盐哈希，不落明文）
    → 签发访问凭证
    → 进入空态引导（提示先导入材料，而非展示空对话）
```

登录后所有请求携带凭证；凭证过期时要求重新登录，不静默降级为匿名访问。登出使当前凭证失效。

**规则：**
- 未认证请求访问任何业务接口一律拒绝，返回 401；
- 已认证但访问不属于自己的资源返回 404/403，并记录安全日志；
- 注册页在提交前须展示隐私政策与数据用途说明（见 NFR-6）；
- 邮箱注册不要求邮箱验证（本期），但需保留后续加验证的扩展点；
- 同一邮箱重复注册必须返回明确提示，不得静默创建重复账号或泄漏该邮箱已注册以外的信息。

### 4.2 文档导入与索引

```text
用户选择文件或粘贴文本
    → 校验格式与大小
    → 创建文档记录（PENDING）
    → 立即返回 202 + documentId        ← 请求到此结束，不等待索引
    ─────────────────────────────────
    后台任务（独立于请求生命周期）
    → 认领任务 → PROCESSING
    → 提取文本
    → 切分并生成 Chunk
    → 调用 embedding
    → 写入向量库与 Chunk 元数据
    → 文档状态 READY
```

**导入必须是异步的**：索引耗时随文档长度线性增长（逐 Chunk embedding），同步执行会让单个请求占用线程数十秒到数分钟，既违反可用性口径，也会被反向代理的默认超时切断。

失败时进入 `FAILED`，保留失败原因和可重试入口；不得把未完成索引的文档当作可检索内容。**请求中断不等于索引失败**——任务独立于请求存在，用户通过状态查询获得最终结果。

技术实现（数据库当队列、不使用 `@Async`、不使用消息队列）见 `docs/ARCHITECTURE.md` §4.1。

### 4.3 知识库问答

```text
用户提出问题
    → 检索 Top-K Chunk
    → 判断是否达到相关性阈值
    → 组装带引用上下文
    → 生成回答
    → 返回回答、引用和 trace 摘要
```

无相关内容时返回明确的“当前知识库没有足够依据”，不得使用无引用的确定性措辞编造个人经历。

### 4.4 JD 分析

```text
用户粘贴一份 JD
    → 解析岗位信息、技术栈、经验要求和疑点
    → 检索个人简历/项目材料
    → 生成匹配度、优势、差距和建议
    → 展示原文引用
```

JD 分析结果默认只展示，不自动写入长期记忆或知识库；用户主动保存时再进入后续审批/持久化流程。

### 4.5 模拟面试

```text
用户选择岗位或输入 JD、选择主题
    → Agent 提出基础问题
    → 用户回答
    → Agent 基于项目材料递进追问
    → 至少完成基础、深挖、压力三轮
    → 生成评估报告与弱点候选
    → 用户整批确认或部分确认
    → 确认项写入 Memory
```

拒绝或未确认的弱点候选不得写入长期记忆。

### 4.6 投递记录

```text
用户自然语言表达投递信息或使用记录入口
    → 提取公司、岗位、状态、日期等字段
    → 展示解析结果
    → 写入或更新 Application
```

投递记录属于低风险业务写入，按 BRD 规则无需 HITL；字段不完整时先要求补充，不得猜测关键字段。

### 4.7 简历要点生成

```text
用户选择 JD 与个人经历
    → Agent 生成 3~5 条草稿
    → 用户逐条编辑、确认或拒绝
    → 仅确认项写入目标知识库
```

生成阶段不得产生持久化副作用；拒绝的草稿不保存。

## 5. 功能需求

### 5.1 FP-1 文档导入与 RAG 检索（P0）

#### PRD-FP-1.1 文档接收

**输入：** 文件上传或文本粘贴，附带可选标题、文档类型和标签。

**支持格式：**

| 格式 | 处理 | 规则 |
|---|---|---|
| Markdown | 支持 | 保留标题层级作为 Chunk metadata |
| Plain text | 支持 | 按空行和固定长度切分 |
| PDF 纯文本 | 有条件支持 | 仅抽取文本，不保证表格结构 |
| PDF 扫描件/复杂表格 | 不支持 | 提示用户复制为 md/txt 后重新导入 |

**业务规则：**

- 原始文件副本保留在配置的本地数据目录；文件路径不得直接作为跨用户可见信息返回。
- 文档必须归属一个 `user_id`。
- **导入接口是异步的**：请求成功只代表任务已创建，返回 `202` + `documentId`，不代表索引完成。响应体必须能让调用方区分「已受理」与「已完成」。
- **请求中断不取消任务**。客户端超时、连接断开、用户关闭页面，后台索引都应继续执行至终态。
- 同一文档重复提交：以「整文档重导」为准，靠向量 ID（`docId#seq#indexVersion`）的幂等性避免重复向量；**但要防止同一用户并发提交同一份内容产生两条并行任务互相覆盖**，需要提交侧的幂等保护（同一 `user_id` + 内容指纹在已有进行中任务时直接返回该任务）。

**验收：**

- md/txt 能进入索引流程并最终成为可检索文档。
- 提交大文档时接口快速返回（不等待索引完成），状态可轮询到 `PROCESSING` → `READY`。
- 提交后立即断开连接，任务仍能跑到终态。
- 不支持的 PDF 能返回可理解的失败原因和替代建议。
- 空文件、无法读取或提取文本为空时进入 `FAILED`，不写入空 Chunk。

#### PRD-FP-1.2 切分与索引

每个 Chunk 至少保留以下业务信息：

- `document_id`、`chunk_id`；
- 原文文本；
- 顺序号、标题/章节路径；
- 起止位置或可复现的引用定位信息；
- `user_id`；
- 创建时间和索引版本。

切分要求：

- md 优先按标题层级切分，再对过长章节进行长度切分；
- txt 按段落和长度切分；
- 保留适度重叠，具体 chunk size/overlap 在评测集上确定；
- 修改切分策略或 embedding 模型时必须支持重建索引；
- 索引写入应具备可重试性，避免重复写入导致引用重复或脏数据。

#### PRD-FP-1.3 相似度检索

**输入：** `user_id`、自然语言查询、可选文档类型/标签过滤、Top-K（默认 5）。

**输出：** 按相关性排序的 Chunk 列表，包括文本、文档名称、章节路径、相关性分数和引用定位。

**规则：**

- 检索只能命中当前用户的数据；
- 低于相关性阈值的结果不应强行注入回答；
- Chroma 不可用时按 NFR-3 降级为 MySQL 关键词检索，并明确标记结果为降级结果；
- Ollama 不可用时停止新索引任务，向用户提示嵌入服务离线。

#### PRD-FP-1.4 引用问答

回答必须能够将依据映射到：

```text
[文档名 > 章节/段落]
```

验收要求：

- 正常问题返回回答和至少一个可定位引用（若知识库存在足够相关内容）；
- 无答案问题返回明确拒答或信息不足提示；
- 引用文本必须来自实际检索 Chunk，不允许由模型虚构文档名或章节；
- 单次 RAG 检索（包括嵌入）目标 ≤ 2 秒，作为 NFR-1 评测指标。

### 5.2 FP-2 Agent 对话与求职工具（P0，I-2）

#### 技术路线

- 首版使用 JobPilot 自研的最小同步 ReAct runner，控制最大轮次、工具预算、超时、异常回填和终止条件。
- Spring AI 是已落地的基础接入层：负责 Chat/Embedding/Tool Calling 的供应商协议适配；但不让高层 Agent 抽象接管 JobPilot 的 ReAct、HITL 和 trace。
- 不引入 LangChain4j 作为当前运行时依赖；**不引入 LangGraph4j**（已评估，理由与触发条件见 `docs/ARCHITECTURE.md` §1.4.1 / §14.4——它是库不是框架，也不强迫引入 LangChain4j，暂缓是因为「图编排 + checkpointing」与线性 ReAct 循环不匹配）；不直接复制 PaiCLI/PaiSmart 的业务实现。
- 目标不是自研通用 Agent 框架，而是实现一个**范围可控、可解释的领域 Agent**。

#### 迭代内的最小范围

**必须做：**

1. 无工具调用时能直接回答；
2. `knowledge_search` 工具能被调用并回填结果；
3. 一个 JD 分析工具能跑通；
4. 最大迭代次数、工具异常、LLM 超时可控；
5. 每轮 trace 能记录模型、工具、耗时和状态；
6. 一个写入类工具实现 `PENDING_APPROVAL` 和幂等审批。

**可以后置：**

- 多 Agent 计划/执行/审查；
- 上下文自动摘要；
- 工具并行执行；
- 完整投递 CRUD 和统计；
- SSE、WebSocket、完整前端；
- 多模型路由和复杂长期记忆。


#### PRD-FP-2.1 对话上下文

对话由 `Conversation` 和有序 `Message` 组成。每条消息至少具有：

- `conversation_id`、`user_id`；
- 角色：`USER`、`ASSISTANT`、必要时 `TOOL`；
- 文本内容；
- 创建时间；
- 可选关联 `job_description_id`；
- 可选引用列表和 trace 标识。

本期不要求上下文摘要治理；上下文过长时允许提示用户开启新会话或按模型限制截断，并记录可观测信息。

#### PRD-FP-2.2 工具注册

Agent 至少支持以下工具：

| 工具 | 作用 | 副作用 |
|---|---|---|
| `knowledge_search` | 检索用户知识库 | 无 |
| `job_description_analyze` | 解析 JD 并结合个人材料形成分析 | 默认无 |
| `application_create` | 创建投递记录 | 低风险写入，无需审批 |
| `application_update` | 更新投递记录 | 低风险写入，无需审批 |
| `application_query` | 查询投递记录 | 无 |
| `application_stats` | 按状态/时间统计 | 无 |
| `memory_candidate_create` | 生成长期记忆候选 | 必须进入 HITL |

工具调用必须有最大迭代次数，默认 `5`；达到上限时返回当前已获得结果和可理解的中止说明。

**多租户约束**：工具的租户上下文由 runner 在执行前注入，**不得由模型通过参数指定 `user_id`**——模型是外部输入，不能成为越权的入口。工具实现内部同样不得接受模型传入的租户标识。

#### PRD-FP-2.3 JD 分析输出

分析结果至少包含：

1. 岗位基本信息：公司、岗位名称、地点/工作模式（若 JD 提供）；
2. 技术栈与能力要求；
3. 经验/学历/实习要求；
4. 岗位疑点或需要进一步确认的内容；
5. 与个人材料的匹配度（说明评分依据）；
6. 优势清单；
7. 差距清单；
8. 每个关键差距对应的个人材料引用或“未找到依据”。

模型无法确定的字段必须标记为未知，不得补全为事实。

### 5.3 FP-3 Trace 与 HITL（P0）

#### PRD-FP-3.1 Trace

每次 Agent 调用至少记录：

- `trace_id`、`user_id`、`conversation_id`；
- 开始/结束时间、总耗时；
- 输入摘要（敏感内容按后续安全策略脱敏）；
- 使用的模型配置；
- 工具调用顺序、参数摘要和结果状态；
- 输出状态、错误类型；
- token 消耗（外部模型能够提供时）。

Trace 用于排查和演示，不作为用户知识库内容参与检索。

#### PRD-FP-3.2 审批门控

| 操作 | 审批方式 | 确认后动作 | 拒绝后动作 |
|---|---|---|---|
| 简历要点写入 | 逐条 | 写入确认项 | 丢弃该条 |
| 面试弱点写入 Memory | 整批，可部分选择 | 写入选中项 | 未选中项不写入 |
| 知识库文档删除 | 单次确认 | 删除元数据、原文件和向量 | 保持不变 |
| 投递记录写入/更新 | 不审批 | 直接写入 | 校验失败时要求补充 |

审批草稿必须有明确状态，例如 `PENDING`、`APPROVED`、`PARTIALLY_APPROVED`、`REJECTED`、`EXPIRED`。过期或已处理的草稿不得重复执行副作用。

### 5.4 FP-4 长期记忆（P1）

Memory 用于保存短小、结构化、用户级的偏好或弱点，不替代 RAG 文档库。

**允许内容：**

- 求职偏好；
- 面试弱点；
- 已确认的准备计划或表达问题。

**不允许直接写入：**

- 未经确认的模型猜测；
- 长篇文档或需要语义检索的材料；
- 其他用户数据。

每条记忆至少包括：`memory_id`、`user_id`、类型、内容、来源（如面试评估）、置信/说明字段、状态、创建/更新时间。用户可以查看、编辑和删除自己的记忆。

### 5.5 FP-5 模型配置与双路径切换（P0）

本期以配置项级切换为目标，不做多模型路由。至少支持：

- 模型名称；
- API endpoint；
- API key（仅环境变量/安全配置注入）；
- temperature；
- max tokens；
- Agent `max_iterations`，默认 5；
- 超时和重试次数；
- **嵌入与生成路径选择**：`local`（默认，Ollama）/ `cloud`（云端 API），两条路径可分别配置，且切换不需要改动业务代码。

**双路径要求：**

- 业务层只依赖 `EmbeddingPort` / `ChatPort`，不得出现「当前是本地还是云端」的分支判断；
- 本地路径为零边际成本默认项，云端路径的所有调用必须进入 FP-10 计量；
- 路径切换后若 embedding 维度发生变化，必须触发与「换 embedding 模型」相同的处理（重建索引或阻断启动），不得让新旧向量混在同一个集合里；
- 未配置云端凭证时，应用应能正常运行在本地路径上，只在真正调用云端能力时给出明确错误。

模型调用超时超过 30 秒时重试一次，仍失败则返回友好错误并记录 trace；不得无限重试。

#### 注册与登录页

必须支持：

- 邮箱注册与登录；

- **注册前可见**的隐私政策与数据用途说明；
- 凭证过期后的重新登录引导，而不是静默失败。

#### 对话页

必须支持：

- 新建/切换/查看历史会话；
- 输入问题、粘贴 JD；
- 查看回答、工具调用结果摘要和引用；
- 查看加载中、错误、重试状态；
- I-5 叠加 SSE 流式输出，先保证同步回答可用。

#### 知识库管理页

必须支持：

- 文档列表：名称、类型、状态、Chunk 数、导入时间、失败原因；
- 上传或粘贴导入；
- 查看文档 Chunk 预览与引用定位；

#### 账号设置页

必须支持：

看板视图、复杂编辑器、社区功能和移动端不在本期。

### 5.7 FP-7 投递进度完整体验（P1）

`Application` 至少包含：

- 公司；
- 岗位名称；
- 状态；
- 投递日期；
- 来源/链接（可选）；
- 关联 JD（可选）；
- 备注；
- `user_id`、创建/更新时间。

状态枚举首版建议为：`WISHLIST`、`APPLIED`、`SCREENING`、`INTERVIEWING`、`OFFER`、`REJECTED`、`WITHDRAWN`。新增状态需同步更新统计和验收用例。

完整体验支持按状态、时间范围查询，以及总数和各状态数量统计；不要求看板拖拽。

### 5.8 FP-8 简历要点生成（P1）

输入为一份 JD 和用户选择的个人经历/文档。输出 3~5 条草稿，每条包含：

- 要点文本；
- 对应经历依据；
- 与 JD 要求的关联；
- 用户可编辑文本。

只有用户确认的条目才可写入知识库。系统必须能区分“生成成功”和“已持久化”；拒绝或关闭页面不应产生写入。

### 5.9 FP-9 账号、鉴权与租户隔离（P0）

> 本节是多租户产品的地基。**在 FP-9 落地前不对外开放注册**，也不接受真实用户的私密材料。

#### PRD-FP-9.1 账号与凭证

**注册输入：** 邮箱、密码、（可选）昵称。

**规则：**

- 密码长度与复杂度做下限校验，存储为加盐哈希（bcrypt / Argon2 等），**任何情况下不得落明文或可逆密文**；
- 邮箱唯一；重复注册返回明确提示，且不得泄漏「该邮箱已被注册」以外的账号信息；
- 凭证签发与校验由服务端完成，有效期可配置，支持续期与主动失效（登出）；
- 密码、哈希、凭证原文不得出现在日志、trace、错误响应与监控指标中。

**验收：**

- 未携带凭证访问任意业务接口返回 401；
- 携带过期或伪造凭证返回 401，且不泄漏校验细节；
- 登出后原凭证立即失效。

#### PRD-FP-9.2 租户数据隔离

**规则：**

- `user_id` 由服务端从凭证中解析得出，**不接受请求体或查询参数传入**；现有接口中由客户端传入 `userId` 的形态必须在 I-1 移除；
- 所有业务表（Document / Chunk / Conversation / Message / Memory / Application / UsageRecord / ApprovalDraft）必须包含租户归属键，并在数据访问层强制注入过滤条件；
- 向量库的写入与检索必须在 metadata 上带租户键并作为**必填过滤条件**，不得依赖「检索后再过滤」——那会先把别人的数据取出来再丢弃；
- 跨租户访问返回 404 或 403，并记录安全日志（含发起者、目标资源类型、时间，不含资源内容）；
- 删除操作同样受租户约束，不得通过构造 ID 删除他人数据。

**验收：**

- 越权用例全覆盖：用 A 的凭证读取 / 修改 / 删除 / 检索 B 的 Document、Chunk、Conversation、Memory、Application、ApprovalDraft，全部被拒绝；
- 检索接口在 A 的知识库查询时，命中结果中不得出现任何 B 的 Chunk；
- 自动化测试中包含至少一组跨租户负向用例，作为回归门禁。

#### PRD-FP-9.3 数据导出与账号注销

- 导出：按用户维度导出其全部业务数据（文档元信息、对话、记忆、投递记录），格式为结构化文件；导出过程不得泄漏其他租户数据。
- 注销：二次确认并明示影响；确认后删除 MySQL 中的业务数据、向量库中对应向量、以及原始文件，**三处缺一不可**；删除不可恢复。
- 注销请求需幂等，重复提交不产生额外副作用。

### 5.10 FP-10 用量计量与配额（P1）

**目的**：多租户共享同一套模型与向量库资源，单租户的异常用量会直接转化为平台成本并影响其他租户，因此必须有可归集的计量口径。

**计量维度：**

| 维度 | 说明 |
|---|---|
| Embedding 调用量 | 按租户统计字符数或 token 数；本地路径记为 0 成本但**仍计量**，便于后续切换云端时口径一致 |
| LLM token 消耗 | 输入 / 输出分开统计；供应商未返回时标记为不可用，不得估算后当作真实值 |
| Agent 调用次数 | 按 run 统计，含工具调用次数 |
| 存储用量 | 文档数、字符数 |

**规则：**

- 计量记录按租户归集，写入 `UsageRecord`；与 trace 关联以便定位异常消耗；
- **配额采用「预留-结算」而非事后记账**：请求开始前先占额度，结束时按实际用量结算差额，失败/中断时退还。事后记账在并发下会让两个请求同时读到「还有余额」而双双放行，预留模式把它变成先到先得；
- **配额分两层**：① 单租户额度（日/月）——防止单个用户滥用；② 平台级滚动窗口总额度——防止「所有租户都在正常使用」把平台总成本打穿。**只做第一层是不够的**；
- 限流与配额是两个不同机制，都需要：限流按 IP 与用户两个维度（注册、登录按 IP 防注册机；对话、嵌入按用户防刷），超限响应需带 `retryAfterSeconds` 告诉客户端何时可重试；
- 配额超限行为：先提示并在响应中标记，再按配置拒绝新的生成类请求；**只读检索与已导入材料的查看不应被配额阻断**；
- 配额阈值为配置项，不硬编码；
- 用量数据属于用户可见信息，应能在账号设置页查看。

> 实现形态参考见 `docs/ARCHITECTURE.md` §2.2（PaiSmart 的 `RateLimitService` / `UsageQuotaService`）。**只借结构，不借其计费体系**——JobPilot 当前只需要「可归集 + 可限制」，不需要「可收费」。

## 6. 业务状态与数据契约

### 6.1 Document 状态

```text
PENDING ──► PROCESSING ──► READY
                │
                ├──► FAILED ──► PROCESSING（重试，超上限后终态）
                │
                └──► PENDING（进程重启后由 worker 重新接管，避免僵死）

READY ──► DELETING ──► DELETED
```

`DELETED` 数据不可继续出现在检索结果；删除向量失败时必须记录不一致状态并提供重建/清理入口。

**`PROCESSING` 必须有出口**：进程在索引中途退出会让任务永久停留在该状态。worker 启动时须扫描超时仍为 `PROCESSING` 的任务并重置为 `PENDING`；重试次数与下次重试时间记录在任务行上（`retry_count` / `next_retry_at`），重启后策略依然有效。

**状态必须全部可达终态**：任何一个文档最终只能是 `READY`、`FAILED` 或 `DELETED`，不允许长期停留在中间态。这要求重试有次数上限，且每次状态迁移可追踪。

### 6.2 核心业务对象

| 对象 | 必备业务含义 | 关键关系 |
|---|---|---|
| User | 账号主体，**同时是本期唯一租户单元** | 1:1 Credential；1:N 其余业务对象 |
| Credential | 登录凭证（邮箱 + 加盐哈希 + 凭证状态） | 归属 User |
| Document | 用户导入的原始材料 | 1:N Chunk |
| Chunk | 可引用、可检索的文本片段 | 归属 Document；对应向量库 vector entry |
| Conversation | 一次连续对话 | 1:N Message |
| Message | 用户/助手/工具消息 | 可关联引用和 trace |
| JobDescription | 可选的结构化 JD | 可关联 Conversation/Application |
| Memory | 已确认的用户级短条目 | 归属 User |
| Application | 一条投递记录 | 可关联 JobDescription |
| UsageRecord | 按租户归集的用量计量条目（FP-10） | 归属 User；可关联 TraceLog |
| TraceLog | 一次 Agent 调用链路 | 关联 Conversation |
| ApprovalDraft | 待用户确认的副作用候选 | 关联来源操作和用户 |

> **租户键是强制字段**：上表中除 User 自身外的所有业务对象，均必须携带 `user_id`，且该字段的过滤由数据访问层统一注入（见 PRD-FP-9.2）。新增业务表时若漏掉租户键，视为隔离缺陷而非普通遗漏。

### 6.3 引用契约

引用是回答的一部分，不是只存在日志中的调试信息。每个引用至少需要：

- `document_id`、展示名称；
- `chunk_id`；
- 章节/段落定位；
- 引用文本或可安全展示的摘要；
- 与回答的关联顺序。

引用定位必须能够从知识库管理页跳转到对应原文或 Chunk 预览。

## 7. 异常、空状态与降级

| 场景 | 用户可见行为 | 数据行为 |
|---|---|---|
| 未登录 / 凭证缺失 | 返回 401 并引导登录 | 不执行任何业务读写 |
| 凭证过期 | 返回 401，前端引导重新登录 | 不静默降级为匿名，不用缓存身份继续操作 |
| 密码错误 / 邮箱已注册 | 返回统一的凭证错误提示 | 不泄漏账号是否存在以外的信息；记录失败次数用于风控 |
| 跨租户访问资源 | 返回 404 或 403 | 拒绝访问；写入安全日志；**不返回任何他人数据片段** |
| 配额超限 | 提示已达配额并说明重置方式 | 拒绝新的生成类请求；只读检索与已导入材料仍可访问 |
| 云端路径未配置 | 提示该能力需先配置云端凭证 | 本地路径继续可用，不整体不可用 |
| 知识库为空 | 提示先导入文档 | 不调用无意义的回答生成 |
| 无相关 Chunk | 提示没有足够依据 | 允许记录对话，不生成伪引用 |
| 嵌入服务不可用（本地路径） | 提示"嵌入服务离线"并给出排查指引 | 新索引失败，可重试 |
| 云端嵌入或向量库不可用 | 提示正在使用关键词检索 / 服务暂不可用 | 允许降级查询，标记 trace；不能静默伪装为向量检索 |
| MySQL 不可用 | 显示服务暂不可用 | 不确认写入成功，不丢弃客户端可重试请求。**不得改从第二个数据库读取**——见下方约束 |
| LLM 超时 | 重试一次后显示友好错误 | 记录失败 trace，不无限重试 |
| 文件格式不支持 | 告知支持格式和替代方式 | 创建失败记录或不创建业务文档，行为需一致 |
| 文档索引失败 | 显示失败原因和重试入口 | 文档为 `FAILED`，不参与检索 |
| 导入任务排队中 | 显示"处理中"与当前进度，不阻塞用户继续操作 | 文档为 `PENDING`/`PROCESSING`；接口返回 202 + `documentId`，用户轮询状态 |
| 导入超时或连接中断 | 不提示"失败"（任务可能仍在跑），引导用户查询状态 | 任务独立于请求存在；**HTTP 断开不取消后台索引** |
| 导入任务因进程重启中断 | 状态由"处理中"自动恢复为重新排队，最终给出结果 | 超过阈值仍为 `PROCESSING` 的行由 worker 重新接管；**不允许永久停留** |
| Agent 达到迭代上限 | 返回已完成部分并提示中止 | 记录工具链和上限原因 |
| 审批草稿过期/重复提交 | 阻止重复副作用并提示当前状态 | 保持幂等 |
| 账号注销进行中 | 提示注销进度与不可恢复 | 逐步清除三处数据；失败时进入可重试的中间状态并告警 |

所有失败状态都应可关联 `trace_id` 或操作 ID，便于排查。**鉴权、越权与注销三类失败属于安全事件，必须留痕且不可降级为普通日志级别。**

### 7.1 降级的边界约束

**降级目标必须是被明确设计为「可缺失 / 可过期」的层**，例如缓存、关键词检索兜底。**不得把另一个数据库作为降级目标。**

产品层面的后果很具体：用户删除一份含姓名、手机号、前公司的简历，系统确认三处清理完成后，若主库恰好不可用而改从异构副本读取，**这份已删材料会重新出现在用户眼前**。对求职场景而言这不是体验问题，而是隐私事故，直接违反 US-7 与 NFR-6。

因此约定：

1. **不为任何数据库建立异步异构副本作为降级手段。** 缓存的语义是「缓存挂了回源到库」，库是最后防线，不是被绕过的对象；
2. **提高可用性走主库自身的复制与故障转移**（如 MySQL 主从），不走第二套存储；
3. **数据删除、账号注销、数据导出这三类操作在任何降级路径下都不得放宽**——宁可失败并明确报错，不允许返回可能已被删除的数据。

> 「主库不可用」本身是可接受的状态：NFR-9 已声明 99% 可用性、单集群、允许计划内维护窗口。**诚实返回「服务暂不可用」优于返回可能已删除的数据。** 技术实现与判据详见 `docs/ARCHITECTURE.md` §8.1。

## 9. 验收标准

### 9.1 功能验收清单

- [ ] 用户可自助注册、登录、登出；未认证请求访问业务接口返回 401。
- [ ] 密码以加盐哈希存储；密码与凭证不出现在日志、trace 与错误响应中。
- [ ] **跨租户越权用例全通过**：A 无法读取/修改/删除/检索 B 的任何业务对象；向量检索结果中不出现他人 Chunk。
- [ ] 业务接口不再由客户端传入 `userId`，身份一律取自凭证。
- [ ] 用户可导出自己的全部数据；注销后 MySQL、向量库、原始文件三处数据均已清除。
- [ ] md/txt 文档可导入、切分、索引、检索和删除。
- [ ] 纯文本 PDF 可按质量规则处理；扫描件/复杂表格被明确拒绝。
- [ ] 知识库问答能返回实际引用；无答案时不编造。
- [ ] JD 分析包含技术栈、要求、疑点、匹配度、优势和差距，并能引用用户材料。
- [ ] Agent 至少能调用知识库检索和 JD 分析工具，最大迭代次数生效。
- [ ] 模拟面试可完成基础→深挖→压力至少三轮。
- [ ] 面试弱点和简历要点必须经过相应 HITL 后才写入。
- [ ] 投递记录支持创建、更新、查询和统计，数据按租户隔离。
- [ ] Trace 可追踪模型、工具链、耗时、租户和错误，且不跨租户可见。
- [ ] 用量按租户归集；配额超限时生成类请求被拒绝，只读检索仍可用。
- [ ] 嵌入与生成可在本地/云端两条路径间通过配置切换，业务代码无需改动。
- [ ] P1 注册登录页、对话页、知识库管理页、账号设置页覆盖空、处理中、成功、失败和重试状态。
- [ ] P2 SSE 在同步闭环稳定后接入，断流时有错误提示，不影响已完成内容。

### 9.2 检索评测集

建立 20 条固定 QA 对，每条包含问题、期望引用段落 ID 和类型：

| 类型 | 数量 | 要求 |
|---|---:|---|
| 事实型 | 8 | 命中技术定义/用法段落 |
| 比较型 | 5 | 命中比较双方或关键依据 |
| 综合型 | 4 | 命中跨文档关联依据 |
| 无答案型 | 3 | 正确拒答或说明证据不足 |

- `P@5` 目标 ≥ 80%。
- 命中定义为引用段落与期望段落文本重叠 ≥ 50%，或属于同一明确段落。**期望值是段落 ID 而非文档 ID**——按文档匹配会把「检索到了正确的文档但完全没命中相关段落」算作成功，掩盖真实问题。
- I-1 交付、每次改变切分/embedding/检索策略后、I-4 演练前各执行一次。
- 评测语料必须为公开或自造样本，**不得混入任何真实用户的私密材料**。
- 无答案型不能只看检索命中率，还要验证最终回答没有伪造事实。

**数据集格式**：JSONL，一行一例，入库随代码走。跳过空行与 `#` / `//` 注释行，解析错误必须报出行号。（格式参考见 `docs/ARCHITECTURE.md` §2.2。）

**失败必须归因到层**。每条未通过的用例除记录「没过」之外，还要判定它属于哪一类——否则拿到 75% 的 P@5 也不知道该改检索还是改 prompt：

| 归因 | 含义 | 该动哪一层 |
|---|---|---|
| `RETRIEVAL_MISS` | 期望段落根本没进 top-K | 切分 / embedding / 阈值 / top-K |
| `PROMPT_OR_MODEL` | 召回了正确段落，但回答没用好 | prompt 组装 / 模型 / 上下文长度 |
| `MISS_BUT_CORRECT` | 检索没命中，但回答碰巧正确 | 不可作为检索通过的证据，需人工复核 |
| `NOT_LABELED` | 无答案型用例，不适用检索指标 | 只看拒答正确性 |

评测结果按归因分类汇总，而不是只给一个总分。

### 9.3 端到端演练

I-4 前使用 10~20 个真实 JD 完成：

```text
导入材料 → 粘贴 JD → 分析匹配 → 面试准备 → 记录投递 → 查看统计 → 复盘弱点
```

每个 JD 至少记录：流程是否走通、人工介入点、错误、耗时、引用质量和需要 hotfix 的问题。

**演练必须使用至少两个独立账号**，交叉验证：A 的对话、检索与投递统计中不出现任何来自 B 的内容；B 删除文档后不影响 A 的索引与引用。单账号演练无法暴露隔离缺陷，**不作为可发布的验收依据**。

## 12. 待架构设计确认项

以下事项不阻塞本 PRD，但必须在架构设计阶段落定：

1. **租户隔离的落地方式**：租户条件在数据访问层如何强制注入（MyBatis-Plus 拦截器 / 显式基础 Mapper / 其他）；如何保证新增业务表不会漏掉租户键。
2. **向量库侧的租户过滤**：租户键如何写入 metadata、如何作为必填过滤条件、以及换用托管向量库时的等价方案。
3. **鉴权方案细节**：凭证格式与签名算法、过期与续期策略、登出失效机制、密钥轮换；Redis 是否承担凭证黑名单与限流。
4. **存量数据迁移**：I-0 已产生的数据（若存在）如何补租户键并避免脏数据进入检索。
5. **双路径维度一致性**：切换本地/云端 embedding 时维度变化的检测与处理，是否沿用启动自检与阻断策略。
6. Chroma API 版本、collection 命名、删除/重建索引和一致性策略；托管向量库的替换边界。
7. chunk size、overlap、embedding 维度和相似度阈值，以评测集结果决定。
8. 原始文件目录、文件命名、防路径穿越、租户间文件物理隔离与备份/恢复策略。
9. MySQL 表拆分、索引、软删除与 Document/Chunk/VectorEntry 一致性。
10. **账号注销的删除编排**：跨 MySQL、向量库、文件存储的删除如何保证最终一致与可重试。
11. **用量计量口径**：字符数 / token 数的取舍，供应商未返回用量时的处理，计量的幂等与补偿。**2026-10-04 已决（随 I-3c 落地，详见 `UsageRecorder` 口径注释与 ROADMAP §6.9）**：Embedding 记码点字符数（嵌入供应商不返回 token，字符数是唯一拿得到且不撒谎的量）；token 未返回记 NULL 不记 0，Spring AI 的 `EmptyUsage` 占位（0/0）须识别为不可用，汇总侧用 `tokenUnavailable` 显式暴露缺口；计量行独立事务（REQUIRES_NEW），业务回滚不撤销已发生的消耗；失败的模型调用仅 Agent 最终失败处记 FAILED 行。「预留-结算」的幂等与补偿随 I-5 配额一起做。
12. SSE 断线恢复、重复事件和已生成内容的持久化策略。
13. trace 与安全日志中输入/输出的脱敏规则和日志保留周期。
14. 前端具体技术栈；BRD 建议 Vue 3 + Element Plus，但不作为本 PRD 的实现硬约束。**2026-10-06 已决（I-4）**：**Vue 3 + Vite + TypeScript + Element Plus**，独立 `frontend/` 单页应用，dev 用 Vite 代理直连后端 `/api/v1`、build 出静态资源。理由：与参考项目（hm-dianping / sky-take-out）同栈、组件与中文文档最齐、对后端出身摩擦最小；TypeScript 让投递/记忆/文档/用量这些多字段接口不易写错。**SSE 不在本期**（I-5），对话页先保证同步回答可用。

> 「Spring AI 是否能减少 Chat/Embedding/Tool Calling 适配代码」已由 I-0 落地回答：能，且业务层 Port 隔离未破。

## 14. 假设与版本记录

### 14.1 当前假设

- 目标用户为校招 / 社招 / 转行的个人求职者；**机构与组织级场景本期不做**。
- 用户接受「材料托管在平台上」的前提是：用途透明、数据可导出、可彻底删除。任一缺失都会直接削弱注册意愿。
- 首版采用邮箱 + 密码自助注册，不做邮箱验证、第三方登录与邀请制。
- JD 主要通过粘贴或手动导入，不抓取招聘平台。
- 部署方可选择本地或云端 embedding 路径；**面向公众的部署默认应配置云端路径**，本地路径主要用于自用与开发。服务离线时系统应清楚提示，而不是静默产生额外成本。
- 「匹配度」是辅助决策，不代表真实录用概率；产品必须展示依据和不确定性。
- 早期用户量小，容量上限（NFR-7）足以覆盖；触及上限前不做分布式改造。
- 用户能接受计划内维护窗口，但维护需提前公告。
